Why HTTP?

TCP is good for transmitting raw data, but it doesn't provide a standard method of describing that data. HTTP attempts to fill that gap, though how well it fills it depends on the person you ask.

How HTTP?

HTTP is less so a protocol, and more so a structure. This will become obvious as you read more on it.

Request (from the client)

The Header

The HTTP header is the only thing differentiating an HTTP request from any normal TCP connection. All characters transmitted here must be in the ASCII character set.

Request Method

The first part of an HTTP request is the HTTP method. There are many methods specified by the standard, but we will only gloss over the two most important and common ones. These are case sensitive and must always be transmitted as uppercase ASCII characters.

GET

Requests to "GET" some information at an endpoint on the server.

POST

Requests to change some information at an endpoint on the server. It's name is really a historical accident -- it was originally intended to be used for "POST"ing to bulletin board systems, and later forums, but it ended up being used for way more than that.

Uniform Resource Identifier

... is a fancy way of saying a path on the server. As HTTP headers can only contain ASCII characters, we have to have a way to encode certain characters that aren't ASCII. This is where percent-encoding comes into play: all non-ASCII characters are safely converted to a string %hex, where "hex" is the hexadecimal representation of the byte. For example, a UTF-8 space would be represented as "%20".

HTTP Version

Finally, the HTTP version is stored at the end of the first line of the header. It is stored as "HTTP/" + version, such that HTTP 1.1 is written as "HTTP/1.1".

The Header(s)

You thought we were done? This is where we get to the juicy bits... the client identifies itself ("User-Agent"), details which type of content it accepts ("Accepts"), details which languages it accepts ("Content-Language"), details which host it is requesting data from ("Host"), etc.

These are all in the format "Name: Value\n", where \n is a newline character.

The Data (if applicable)

If the request method is one that contains extra data, such as the POST request, this is where that data will be stored.

Response

The response is mostly the same, but contains some important differences.

The Header

HTTP Version

In the same format as the client.

Status Code

This is a decimal number XYY consisting of two parts, the class (X) and the message (YY).

Class

The class of the message (not to be confused with class as in OOP) represents which type of response it is. For example, the class 2 is a success value, 4 means client error, and 5 means server error.

Message

The message is specific to each class, and defines what the error actually is. For example, for status code 404 (class 4, message 04), the status code means "File Not Found", while status code 410 means "Gone".

Status Code Description

This is a (possibly server-specific) description of the error code. Usually these will align with the recommended descriptions in the HTTP standard.

The Header(s)

These describe the response data. For example, the "Compression" header describes which format the data is compressed in. This is most commonly gzip. They are in the same format as the client headers.

Data

The data associated with the URI in the request.
